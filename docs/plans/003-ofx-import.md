# 003. OFX import

**Status:** active (drafted by the slice 2 session before handing over; reviewed and changed by the slice 3 session, see "Changed from the draft") · **Satisfies:** AC21 to AC25, AC39, AC41, with AC34 and AC35 for `import` of an OFX file · **Depends on:** 002

The second importer: OFX statements in the 1.x SGML form (unclosed tags) and the 2.x XML form, read by one scanner into the same `Transaction | Unreadable` outcomes slice 2 defined, fingerprinted from `FITID` (ADR 0008), and written through the same `Store.import_transactions`.

**Door:** one-way. The fingerprint `ofx:<FITID>` is persisted (ADR 0008); `tally import --account NAME FILE` without `--layout` is now the OFX shape of the command line; the unreadable messages' word (`transaction N:`) and the JSON key `transaction` for an OFX file's unreadable entries are part of what `--format json` consumers read. No schema change. A human reads `src/tally/importers/ofx.py` and `src/tally/cli.py` before merging.

## Decisions taken in this plan

- **One scanner, no XML parser.** OFX 2.x is OFX 1.x with closed tags and an XML prolog, so one tolerant scanner reads both. Markup is `<NAME>` (open), `</NAME>` (close), `<NAME/>` (open and close), `<?...?>` (a processing instruction: the XML prolog and `<?OFX ...?>`, skipped) and `<!--...-->` (a comment, skipped). The text up to the next `<` is a value. No `xml.etree`, expat or `html` module runs, so there is no entity expansion, no external fetch and no DTD handling to get wrong.
- **The structure, in SGML's terms.** An open tag followed by a value is a leaf of the aggregate around it, and the next tag closes it (the SGML rule). An open tag followed by another tag is an aggregate and goes on a stack. `</NAME>` closes back to `NAME` if it is open and is ignored otherwise (banks' SGML is loose). An aggregate never contains itself: `<STMTTRN>` while a `STMTTRN` is open closes the open one first, which is how the sample's unclosed `STMTTRN`s end. An empty element (`<MEMO></MEMO>`, `<MEMO/>`) is an empty aggregate. Only a transaction's direct leaves count, so `PAYEE`'s or `CURRENCY`'s inner tags are never taken for the transaction's own.
- **Depth is capped at 64** (AC41): the sixty-fifth open aggregate is `not a statement: tags nested deeper than 64`. Repeated identical tags are siblings by the rule above and cost nothing. The scanner never recurses, and a transaction keeps only the five leaves it reads (`FITID`, `DTPOSTED`, `TRNAMT`, `NAME`, `MEMO`), the first of each, so ten thousand other leaves in one `STMTTRN` cost no memory.
- **Streamed.** The file is read in 64 KB chunks through an incremental decoder; a value, tag or comment longer than 1 MB (no `<` or no closing `>` for a megabyte) is `not a statement: a value or tag longer than 1 MB`. A file that ends inside a tag is `not a statement: the file ends inside a tag`.
- **AC39: a DOCTYPE is refused where the scanner meets it**, whatever comes before it, with `the file declares a DOCTYPE, which statements never do`; any other `<!` declaration (`<!ENTITY`, `<![CDATA[`) is `not a statement: a <! declaration, which statements never hold`. The check is on the bytes as text, before anything could interpret them; nothing in Tally ever resolves a `SYSTEM` or `PUBLIC` identifier.
- **The file must be OFX:** the first tag is `<OFX>` (else `not a statement: the first tag is not <OFX>`), and it holds at most one statement aggregate (`STMTRS` or `CCSTMTRS`; a second is `the file holds more than one statement`). FITIDs are unique per account, so two accounts' statements imported into one would silently drop each other's rows as "already there".
- **Encoding, once, from the header.** SGML: `ENCODING:UTF-8` is `utf-8`; otherwise `CHARSET:1252`, `CHARSET:NONE` or no `CHARSET` is `cp1252` (the OFX 1.x default, a superset of ASCII), `CHARSET:ISO-8859-1` or `8859-1` is `latin-1`, and any other `CHARSET` is `not a text file: CHARSET is not 1252, ISO-8859-1 or NONE`. XML: a UTF-8 byte order mark wins; else the prolog's `encoding="..."`, looked up by Python's codecs and refused unless it writes `<OFX>` as those five ASCII bytes (UTF-16, UTF-7, EBCDIC); else `utf-8`. The message names Python's canonical codec name, never the file's text. A decoding error anywhere, or a NUL character, refuses the whole file as `not a text file...`, as for CSV.
- **Entities are decoded by Tally's own few lines:** `&lt;`, `&gt;`, `&amp;`, `&quot;`, `&apos;`, `&nbsp;` and numeric references (`&#38;`, `&#x26;`, ASCII digits only). A reference to NUL, a surrogate or beyond U+10FFFF stays as written: NUL stops SQLite's text functions and a surrogate cannot be stored. Anything else with `&` is text.
- **The currency check is before any row is written.** `CURDEF` is met before the first `STMTTRN` in any real statement; one that is not three ASCII letters is `not a statement: CURDEF is not a currency code`, and one that is not the account's raises `NotAStatementError("the file is in GBP but the account is in EUR")` (AC24). It is raised from inside the outcomes iterator, which `import_transactions` consumes under the lock, so the rollback makes "nothing written" hold wherever in the file it is met; the import record is rolled back with it. A file with no `CURDEF` takes the account's currency, as a CSV does.
- **A transaction's outcome** is decided when its `STMTTRN` closes (explicitly, by the next `STMTTRN`, by an enclosing close, or at the end of the file), checked in this order: no `FITID` is `no FITID` (AC41), no `DTPOSTED` is `no DTPOSTED` (AC25), no `TRNAMT` is `no TRNAMT`; a `DTPOSTED` whose first eight characters are not eight ASCII digits making a real day is `DTPOSTED is not a date` (read with `date(y, m, d)`, not `strptime`, whose `%Y%m%d` takes `2026111` as 1 November); a `TRNAMT` that is not OFX's one number shape (`[+-]` then ASCII digits with an optional `.` fraction) is `amount is not a number` (so `12,34` is, AC25), then `to_minor`'s own refusals. The description is `NAME`, else `MEMO`, else empty. `Unreadable.line` holds the transaction's 1-based position.
- **The fingerprint is `ofx:<FITID>`** (ADR 0008), the `FITID` trimmed; two `STMTTRN` with the same `FITID` in one file are one transaction (the second is "already there"), which is what a bank's promise of uniqueness means.
- **The word for a position is `cli.py`'s:** `transaction N:` for an OFX file and `line N:` for a CSV on standard error, and the same word as the JSON key (`{"transaction": 2, "reason": ...}` for OFX, `{"line": 3, ...}` for CSV, unchanged).
- **`--layout` with an OFX file stays exit 2**; `tally import --account savings samples/savings.ofx` is the whole command (AC21). `--verbose` logs the form, the encoding and the transaction count, never a value.
- **Tests:** `tests/test_ofx.py` for the importer alone, `tests/test_ofx_import.py` for the command through `main`, with `tests/test_import.py::Place` reused and a `savings` account in GBP added to it.

## Changed from the draft

- **Entities:** the draft used `html.unescape`. It follows HTML5: about 2,200 names, forms without the semicolon (`&ampfoo` is `&foo`, `&copy` is `©`), `&#x80;` as `€` and `&#0;` as U+FFFD (all probed). Neither OFX form means any of that, so Tally decodes the five XML entities, `&nbsp;` and numeric references itself.
- **`TRNAMT`:** the draft used `parse_amount(text, ".", ",")`. That accepts thousands separators, brackets and currency symbols, none of which OFX writes, and reads `1,234` (a European bank's 1.234) as 1234.00 without a word. OFX has one number shape; anything else is `amount is not a number`.
- **`DTPOSTED`:** the draft did not say how; `strptime` was the obvious choice and takes seven digits as a date (probed), so the eight digits are checked and `date()` decides.
- **No `NAME` nor `MEMO`:** the draft made it unreadable (`no NAME`). OFX makes `NAME` optional (a `PAYEE` aggregate may stand instead), and a transaction with an amount and a `FITID` is still money; it imports with an empty description.
- **Added:** an aggregate never contains itself (the draft named only `STMTTRN` and `BANKTRANLIST`); an empty element is an empty aggregate; only the five leaves are kept; the DOCTYPE is refused wherever the scanner meets it, not only in the first kilobyte, and any other `<!` declaration too; the first tag must be `<OFX>`; a second statement is refused; `CURDEF` must be three letters before it goes into a message; an unknown `CHARSET` or a non-ASCII-compatible declared encoding is refused; a NUL, surrogate or out-of-range numeric reference stays literal; the JSON key is `transaction` for OFX (the draft kept `line`, which would call a transaction's position a line).
- **Tests:** the command's tests get their own file beside `test_import.py`, as the CSV importer and command have theirs.
